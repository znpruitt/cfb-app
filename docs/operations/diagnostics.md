When data looks wrong on a surface, diagnose **upstream-first**. The single most common mistake is starting at the UI; by then the fault is almost always several layers up.

## Debugging order (never start at the UI)

```text
1. API response          ← is the provider payload itself right?
2. normalization layer    ← did schedule normalization preserve it?
3. canonical game model   ← is the AppGame identity/week correct?
4. attachment layers      ← did scores/odds/ownership attach to the right game?
5. UI                     ← only after 1–4 check out
```

Diagnose in this order because every downstream layer _attaches onto_ the schedule-derived canonical game (see [../architecture/game-data-flow.md](../architecture/game-data-flow.md)). A wrong score or owner on screen is usually a mis-_attachment_ (layer 4) or a mis-_resolved identity_ (layer 3), not a rendering bug (layer 5).

## Diagnostic surfaces & their auth

All debug/admin diagnostics are gated — none are public.

- **`/debug` and `/admin` pages** are gated by the Clerk middleware and require the `platform_admin` role (fail closed: signed-out → `/login`, wrong role → `/`).
- **`/api/debug/*` endpoints** are **route-gated** by `requireAdminAuth` (not the page middleware), so the `ADMIN_API_TOKEN` fallback works for machine callers. They return `401` JSON otherwise.

See [../architecture/auth-and-privacy.md](../architecture/auth-and-privacy.md) for the full gating model.

## What to inspect at each layer

- **Schedule / identity (layers 2–3):** does the canonical `AppGame` carry the expected `providerGameId`, `week`/`providerWeek`/`canonicalWeek`, and resolved `canHome`/`canAway`? An unresolved team means a `teamIdentity` miss — check the alias map (stored global > year > seed) rather than patching downstream. Postseason weeks use `canonicalWeek = maxRegularSeasonWeek + providerWeek`; a bowl/CFP game filed under the wrong week is a canonical-week issue, not a UI filter issue.
- **Score attachment (layer 4):** attachment precedence is provider-event-id → home/away+week → reversed pair+week → pair+date (±18h). A missing score is usually an unattached row; a swapped score is an orientation (`direct`/`reversed`) issue. Score diagnostics forward `refresh=1` + admin auth to inspect the authorized path.
- **Odds attachment (layer 4):** one-to-one, ±24h of `commenceTime`. `date_mismatch`/`unmatched_pair` = no candidate; `ambiguous_pair` = it refused to guess between multiple. Odds never create canonical identities.
- **Classification / lifecycle:** time-dependent state (preseason/awaiting-kickoff/live) is decided in consumers from a cached time-invariant fact plus request `currentDate` — reproduce with the same `currentDate`, not an implicit "now" (see [../architecture/standings.md](../architecture/standings.md)).
- **Provider quota:** public reads are pure cache readers and spend nothing; if data is stale, the fix is an **authorized** refresh (admin `refresh=1` / cron), not a public re-fetch. Check odds-usage/quota state before assuming a provider outage.

## Provider Data Status panel (PLATFORM-086A)

`/admin/diagnostics` includes a **Provider Data Status** panel — the first stop when a dataset looks stale or missing. Per provider dataset (scores/schedule/odds/rankings/conferences/game-stats) it shows the durable refresh status — the newest attempt's **explicit state** (refresh in progress / attempt appears interrupted / last attempt succeeded / partial / failed / **completed — no applicable data**), or, when **no** PLATFORM-086A refresh-status record exists yet, a cache-aware no-history state (_serving cached data · no refresh history recorded_ when cached data exists, _no cached data or refresh history_ when it does not, or a conservative _no refresh history recorded_ when availability cannot be proven) — plus last success + age, last error, rows committed, partial-failure/failed partitions, source — alongside cache-only **missing-data diagnostics**:

- **Scores:** a completed slate (latest kickoff > 6h ago, derived from the canonical schedule) with no cached **terminal** score. Coverage requires a canonical terminal classification (final, or a canceled game that will never have a final) — a mid-game refresh that left only an in-progress numeric row does **not** count as covered, so the missing-final warning is not suppressed until finals actually land.
- **Game stats:** a completed slate whose canonical stat-producing games lack complete durable evidence. **Expected games come from the canonical schedule/slate** (`canonicalSlate.ts`), and **completeness is the participant-verified `evaluatePartitionCoverage`** — **not** cache-key existence and **not** a raw usable-row count. Durable game-stat evidence attaches to canonical games (provider game id + partition + oriented participant validation); a record with `games: []`, all rows dropped in normalization, or rows whose participants don't match the schedule contributes no coverage. `src/lib/gameStats/coverage.ts` is only a limited cached-**presence** probe for the admin cache-state panel — cached-row usability alone is not the canonical coverage model. Only **stat-producing** games are expected: disrupted games (canceled/postponed/suspended/delayed) are excluded by the canonical slate / evidence authority, so a slate composed _entirely_ of disrupted games is not applicable and raises no missing-stats warning. Status classification is **separator-agnostic** — the shared `gameStatus` classifier normalizes provider/cache enum labels (`STATUS_CANCELED`, `STATUS_POSTPONED`, hyphenated or spaced variants) to tokens before matching, so an underscore-delimited enum is not silently treated as stat-producing. Partial coverage (some expected games missing) surfaces as an info note rather than being hidden by the key's presence.
- **Schedule:** no current-season schedule cached, a partial last refresh, or a schedule older than the weekly policy during an active season.
- **Rankings:** no **usable** rankings — missing, or a cached record whose `response.weeks` is empty (pre-poll / schema-drifted) — or usable-but-older than the weekly policy during an active season. Record presence alone is not coverage.
- **Odds:** recency of the **selected season's CANONICAL** served odds cache — the exact key the default (unfiltered) UI request reads (`defaultOddsCacheKey`). A game without an offered line is **not** a failure — odds are classified as available/stale/not-offered, never errored for missing lines. Staleness derives from that canonical `odds-cache` entry's `lastFetch` only — **not** the newest across filtered markets/bookmakers variants (a filtered refresh must not make the served snapshot look fresh) and **not** the global quota-observation timestamp; absence of the canonical snapshot is reported as unknown, never treated as fresh.

Each dataset card reflects its **canonical target scope** for the selected year (PLATFORM-086A-SCOPED), shown as a small scope chip on the card (e.g. _global_ for conferences, _year 2026_ for schedule/scores/rankings/game-stats, _2026 odds (canonical)_ for odds). Only an operation covering the card's **whole** target advances it: the schedule year card advances only on a **full-year** schedule refresh, and the scores year card advances only on an aggregate refresh that covers **every applicable** partition (PLATFORM-086A-SCOPED-STATUS review remediation). Anything narrower — a refresh for a different year, a targeted schedule repair (a single `seasonType` or a single week), a single score/rankings partition, a **week-specific** score refresh, an aggregate score subset that omits an applicable sibling (e.g. postseason-only while regular is also applicable), a single game-stats week, or a filtered odds query — is recorded against its own target and **never** advances the card's canonical status, so a targeted repair can never make the selected year's whole-target status look successful or fresh. (A full-season game-stats card therefore stays "no refresh history" until a full-season backfill exists — a single ingested week does not populate it.) Legacy pre-scoped records are kept for deep diagnostics but are never presented as selected-year truth. A completion token that resolves a different dataset or scope than it was begun for is **rejected** (the status write is skipped), so a concurrent cross-year/cross-partition refresh cannot cross-contaminate another target's card.

These diagnostics are **cache-only** — they read the canonical schedule and durable caches and never spend provider quota to determine status (the panel's status `GET /api/admin/provider-status` makes no provider call; live CFBD usage is fetched separately as an authoritative read). Reading the panel answers "when did this last succeed / is it stale / did the last attempt fail / is expected data missing / how much quota remains" without touching logs or storage.

The same panel exposes the operator **global pause** and **per-dataset enable/disable** controls (see [deployment.md](deployment.md) → "Provider-refresh observability & controls"). Since PLATFORM-086F2D1/D2 it exposes **no manual refreshes**: System Health owns automation gates, provider/cache status, quota observation, and storage diagnostics, while **Data Maintenance & Recovery** (`/admin/data/cache`) owns every provider-spending repair action — the manual dataset refreshes and the explicitly confirmed score-attachment recovery — each with its per-action cost/scope disclosure. A failed manual refresh never advances the dataset's last-success timestamp. The failure message is **cache-state-aware** (never a blanket "prior-good data still serving"): with cached data available it reads "prior-good cached data is still serving," with none it reads "no cached data is available" (a cold first failure with no cache), and when availability can't be proven it says so conservatively — a historical `lastSuccessAt` (shown separately as "Last success") never overrides current cache absence.

### Full-season schedule refresh authority & rollover boundary (PLATFORM-086E1A)

Every full-season schedule writer (the full-year `/api/schedule?bypassCache=1` refresh, the season-transition cron, the historical repair) drives one authority (`refreshFullSeasonSchedule`), so the **schedule** year card's provider-refresh status now reflects it uniformly. Diagnostic reading of the schedule status `lastError.code`:

- `schedule-partition-fetch-failed` / `schedule-partition-invalid-payload` / `schedule-partition-schema-drift` — a required regular/postseason partition was uncertain (`failedPartitions` names which); the aggregate was rejected and prior-good retained.
- `schedule-empty-replacement-rejected` — the provider returned zero games over a populated prior-good schedule (rejected, not written).
- `schedule-durable-commit-failed` — the durable transaction failed; nothing published.
- `schedule-cfbd-api-key-missing` — credentials absent; the exact year-scoped attempt was begun and resolved (never left dangling).

A **concurrent** full-year refresh returns HTTP `409` with code `refresh-in-progress` and makes **no** provider request (a nonexpired `schedule-refresh-control/<year>` lease is held) — it records **no** attempt, so it never appears as a failure. A prior-durable-read outage fails fast as `canonical-context-unavailable` **before** any attempt, so the card shows no new attempt (not a dangling one).

**Automatic season rollover** (`/api/cron/season-rollover`) is cache-only and makes no provider call. It requires a **structured** CFP national championship (`playoffRoundSource === 'cfbd-structured'`) with a confirmed complete final (via the centralized score attachment) plus the seven-day gate, evaluating each season year independently; the "latest postseason game" fallback is gone. When it does not roll, the per-year result's `reason` explains why — `no-season-schedule` / `no-structured-championship` / `score-missing` / `not-final` / `disrupted` / `waiting-period` are ordinary skips (no mutation), while a genuine durable read failure surfaces as `read-failed` in `errors` (success `false`), never a benign skip. `findNationalChampionshipGameDate` on the admin cache page is presentation-only and does not drive rollover.

### Game-stats scheduler execution logging (PLATFORM-086F1)

The QStash response records the cron route's JSON result, and provider-refresh status records real target-resolved work — but historically the app emitted no dedicated structured log for every scheduler decision, so a harmless early exit such as `no partition inside the polling window` was visible in QStash yet hard to find in Vercel logs. **PLATFORM-086F1** closes that gap: `GET /api/cron/game-stats` now emits exactly ONE secret-safe, single-line JSON event per invocation — `console.log(JSON.stringify(event))`, observed in **Vercel Runtime Logs** — for skips, every outcome (including `partial`), authentication failures, and unexpected exceptions alike. It is runtime-only: no durable heartbeat, no AppStateStore record, no admin-panel card, and **no provider-refresh attempt is ever fabricated** (no-target and paused/disabled checks still exit before quota/provider/attempt work — an observability addition, never an H3E behavior change).

The event carries ONLY this allowlisted operational shape (`src/lib/gameStats/cronExecutionLog.ts`), never a request/response object, thrown error, provider payload, environment value, URL, credential, or authorization header:

- `event`: always `"game-stats-cron"`.
- `result`: `skipped` | `success` | `partial` | `no-op` | `failure`.
- `reason`: a stable machine reason — `cron-secret-not-configured` / `cron-authorization-invalid` (auth), `automation-paused-or-disabled` / `canonical-context-unavailable` / `no-polling-target` (skips), `quota-<usage-unavailable|usage-untrustworthy|below-reserve>` (quota refusal), `cfbd-api-key-missing`, `provider-fetch-failed`, `ingestion-failed`, `unexpected-error`, or the interpreter's exact outcome reason (`empty-response`, `written-clean`, `written-mixed`, `partially-merged`, `unchanged-clean`, `unchanged-mixed`, `stale-clean`, `stale-mixed`, `invalid-payload`, `no-persistable-observations`, `conflict`, `unavailable`, `indeterminate`). The free-form canonical-context reason and any thrown message are deliberately excluded.
- `year`, nullable `week`, nullable `seasonType`: the resolved partition (`week`/`seasonType` set only once an exact target resolves).
- `quotaChecked`: true once the CFBD `/info` quota probe runs (stays true even if it throws or yields untrustworthy usage).
- `providerCallAttempted`: true only for the billed CFBD `/games/teams` data request — never the `/info` probe.
- `committedGames`: the confirmed durable-commit count (0 on skip/no-op/failure; nonzero only for `success`/`partial`).
- `durationMs`: whole-invocation duration, a nonnegative integer.

Emission is best-effort (a serialization or console failure never alters the HTTP response or masks a thrown error) and happens exactly once, from a single `finally`. `cfbd-api-key-missing` and the defensive `ingestion-failed` catch are unreachable at runtime (an unreadable key makes the quota gate refuse first with `usage-unavailable`; H2 funnels every expected ingestion fault into a typed outcome), so their mappings are guarded by a static source-pin rather than fabricated states. The broader admin-diagnostics information-architecture redesign is **PLATFORM-086F2** (in progress); the independent "last scheduler check" durable heartbeat it called for has since shipped as the **PLATFORM-086F2E1** execution receipts (see "Scheduler execution receipts" below), which stay distinct from provider-refresh status so a harmless scheduler check never fabricates provider activity.

### Live-score scheduler execution logging (PLATFORM-086B1)

**PLATFORM-086B1** adds the same runtime-event contract to the live-score polling engine: `GET /api/cron/live-scores` emits exactly ONE secret-safe, single-line JSON event per invocation — `console.log(JSON.stringify(event))`, observed in **Vercel Runtime Logs** — for skips, every polling outcome (including `partial`), authentication failures, and unexpected exceptions alike. **The route is now ACTIVE in production (PLATFORM-086B2B, activated 2026-07-28):** the external QStash schedule `turfwar-live-scores-3m` invokes it every 3 minutes, gated by both `isAutoRefreshAllowed('scores')` conditions (global pause off + the `scores` dataset enabled); a delivery with either gate closed logs `skipped / automation-paused-or-disabled`, and a gates-open delivery with no in-window game logs `skipped / no-polling-target` (`quotaChecked: false`, `providerCallAttempted: false`). The event is runtime-only: no durable heartbeat, no AppStateStore record, no admin-panel card, and **no provider-refresh attempt is ever fabricated** (auth failure, pause, unavailable context, and no-target all exit before any scoped attempt, quota probe, or provider call). A billed CFBD `/scoreboard` or `/games` call happens only when a game is inside the kickoff window and quota policy passes — ordinary in-season monitoring, not pending activation.

The event carries ONLY this allowlisted shape (`src/lib/liveScores/cronExecutionLog.ts`), never a request/response object, thrown error, provider payload, environment value, URL, credential, or authorization header:

- `event`: always `"live-scores-cron"`.
- `result`: `skipped` | `success` | `partial` | `no-op` | `failure`.
- `reason`: a stable machine reason — `cron-secret-not-configured` / `cron-authorization-invalid` (auth), `automation-paused-or-disabled` / `canonical-context-unavailable` / `no-polling-target` (skips), `quota-<usage-unavailable|usage-untrustworthy|below-reserve>` (quota refusal), `cfbd-api-key-missing`, `provider-fetch-failed`, `durable-commit-failed`, `unexpected-error`, one of the scoreboard classifications (`scoreboard-invalid-payload`, `scoreboard-schema-drift`, `scoreboard-empty-unexpected`, `scoreboard-no-target-matches`, `scoreboard-targets-missing`, `scoreboard-unchanged-clean`, `scoreboard-written-clean`, `scoreboard-written-partial`), or one of the final-reconciliation classifications (`final-reconciliation-confirmed`, `final-reconciliation-partial`, `final-reconciliation-not-confirmed`, `final-reconciliation-invalid-payload`, `final-reconciliation-empty-unexpected`).
- `year`: the season year (resolved from the same start instant as an auth failure, so it is always present).
- `mode`: `scoreboard` | `final-reconciliation` | `null` (null before a target resolves).
- `targetGames`, `targetPartitions`: the count of targeted canonical games and exact week partitions this run (0 outside a resolved target).
- `quotaChecked`: true once the CFBD `/info` quota probe runs (stays true even if it throws or yields untrustworthy usage; a skip before target resolution never sets it).
- `providerCallAttempted`: true only for the ONE billed CFBD `/scoreboard` or `/games` data request — never the `/info` probe.
- `committedGames`: confirmed durable score/status changes (0 on skip/no-op/failure and on a metadata-only confirmation clear; nonzero only when a served score actually changed).
- `durationMs`: whole-invocation duration, a nonnegative integer.

Exact scoped-status behavior to know when reading it:

- **Every targeted week partition gets its OWN scoped provider-refresh attempt** (`weekPartitionScope(year, providerWeek, seasonType)`), begun BEFORE any quota, credential, or provider work and resolved exactly once — `succeeded` (durable change, all targeted games present), `partial` (a durable change with some targeted games missing from the response — recorded via `partialFailure: true`, which the status store writes as `latestAttemptOutcome: 'partial'`, not `succeeded`), `no-op` (valid response, no change), or `failed` (provider/validation/durable failure, or a partition with targeted games missing and NO durable change, prior-good retained). A live run **never writes the selected-year aggregate score status** (`year` rollup) — that scope stays owned by the manual/aggregate `/api/scores` refresh, so a per-partition live poll can never advance or clear the year-level status.
- **One global `/scoreboard` call can touch several partitions**, but each partition keeps its own attempt and outcome; a single quota refusal or provider-fetch failure resolves ALL begun partition attempts as truthful failures.
- **Scoreboard finals are written immediately but recorded pending a `/games` confirmation** (`pendingFinalConfirmationIds` on the exact child cache entry); a later final-reconciliation run confirms them against `/games` and clears the metadata (a same-score confirmation is a metadata-only change: `committedGames: 0`, standings not invalidated). Monotonic protection (`scheduled ↛ in-progress ↛ final`) and per-row freshness stamps run against the reconciled prior score (child + season-wide aggregate), so a transient row can never regress a better cached score, and served-score freshness is never fabricated.

**PLATFORM-086C2** adds the same runtime-event contract to the automatic Odds polling cron: `GET /api/cron/odds` emits exactly ONE secret-safe, single-line JSON event per invocation — `console.log(JSON.stringify(event))`, observed in **Vercel Runtime Logs** — for skips, every outcome, authentication failures, and unexpected exceptions alike. **The route is ACTIVE in production: the deployment-runbook §8g operator sequence provisioned the external QStash schedule `turfwar-odds-hourly` (hourly).** Public/member `/api/odds` is a durable-cache-only reader (never a self-fetch, never quota) reflecting cross-instance commits within a bounded 120 s memo. Each hourly delivery is gated by both `isAutoRefreshAllowed('odds')` conditions (global pause off + the `odds` dataset enabled); a delivery with either gate closed logs `skipped / automation-paused-or-disabled`. The hourly cadence is a CEILING — the pure policy issues a billed request only when the freshest completed signal exceeds the cadence threshold (baseline 6 h; 2 h inside the 6 h before a slate's first America/Chicago kickoff), an eligible in-horizon game exists, and the durable backoff is inactive — so most deliveries are provider-free `skipped / refresh-not-due` or `skipped / no-eligible-target`. The event is runtime-only: no durable heartbeat, no AppStateStore record, no admin-panel card, and **no provider-refresh attempt is ever fabricated** (auth failure, pause, unavailable context, no-eligible-target, not-due, backoff, an active lease, a failed/untrustworthy quota probe, and the reserve refusal all exit before any scoped attempt is begun; only a genuinely-due, quota-cleared run begins the ONE exact attempt).

The event carries ONLY this allowlisted shape (`src/lib/odds/cronExecutionLog.ts`), never a request/response object, thrown error, provider payload, environment value, URL, credential, or authorization header:

- `event`: always `"odds-cron"`.
- `result`: `skipped` | `success` | `no-op` | `failure`.
- `reason`: a stable machine reason — `cron-secret-not-configured` / `cron-authorization-invalid` (auth); `automation-paused-or-disabled` / `canonical-context-unavailable` / `no-eligible-target` / `refresh-not-due` / `automatic-backoff` / `refresh-in-progress` / `quota-reserve` (skips); `quota-probe-failed` / `quota-usage-untrustworthy` (quota probe failure — see the HTTP-status note below); `odds-api-key-missing` (config failure); `provider-fetch-failed` / `odds-invalid-payload` / `odds-schema-drift` / `odds-empty-unexpected` (provider/payload failure); `durable-commit-failed` / `polling-state-unavailable` / `refresh-control-unavailable` / `closing-maintenance-failed` (state/commit failure); `unexpected-error`; `empty-response` / `stale-observation` (no-op); `closing-maintenance` (a closing-only durable change with no refresh due — a success); `written-clean` (success).
- `year`: the season year (resolved from the same start instant as an auth failure, so it is always present).
- `cadence`: `baseline` | `pregame` | `null` (null unless a refresh was due and a request was issued).
- `eligibleGames`: the count of canonical games qualifying for automatic polling this run (0 outside an eligible target).
- `quotaChecked`: true once the quota-free `/sports` usage probe runs (a skip before the probe never sets it).
- `providerCallAttempted`: true only for the ONE billed `/odds` data request — never the `/sports` probe.
- `requestCost`: the estimated `/odds` credit cost (canonical markets × bookmaker groups; 3 for the canonical contract; 0 when no request is due).
- `quotaRemainingBefore`: trustworthy remaining credits from the pre-request `/sports` probe (null before the probe).
- `quotaRemainingAfter`: the post-call remaining — authoritative `/odds` headers when trustworthy, the 402/429 authoritative zero, or a conservative estimate; null when no billed request happened.
- `rowsCommitted`: durable odds rows committed (nonzero only on a `written-clean` success).
- `closingStoreChanged`: true when cache-only closing-line maintenance wrote the durable store this run (independent of whether a provider refresh occurred).
- `durationMs`: whole-invocation duration, a nonnegative integer.

Exact behavior to know when reading it:

- **A quota-probe failure is a `result: 'failure'` at HTTP 200, by design.** `quota-probe-failed` (the zero-cost `/sports` probe transport/HTTP-failed) and `quota-usage-untrustworthy` (its usage headers were missing/malformed → fail closed, no `/odds` issued) return HTTP **200** with `result: 'failure'`, matching the sibling live-scores cron's `quota-usage-unknown → 200 failure` convention — a recoverable next-run condition, not an HTTP-level route error (QStash retries are 0 regardless). **Monitor these on the event `result`/`reason`, not the HTTP status.** The HTTP status is reserved for auth (`401`), provider/payload faults (`502`), state/commit faults (`503`), and config/unexpected faults (`500`).
- **No duplicate billed request across the manual/automatic boundary.** The durable per-target lease serializes a manual `refresh=1` and the cron; the cron RE-CHECKS cadence against the transaction-fresh control the lease acquire returns (plus a fresh raw observation) after acquiring, so a manual refresh completing just before acquisition suppresses a redundant request (`skipped / refresh-not-due`, release-only). QStash at-least-once redelivery re-runs the same idempotent poll; observation ordering makes a re-observed row a monotonic no-op.
- **Quota accounting is conservative and self-healing.** A billed failure with untrustworthy usage headers records a conservative deducted estimate (never leaving an overstated balance); a 402/429 records the authoritative zero (from header trustworthiness, so a malformed `remaining: -1` cannot restore a positive balance); a success with missing headers commits `null` usage into the raw cache rather than a stale pre-spend balance. The next run's `/sports` probe overwrites any estimate with the true balance.

Panel behavior to know when reading it:

- **The newest attempt's state is explicit.** The state line reads the durable `latestAttemptOutcome`, not an inference from the last success/error — so an in-flight, interrupted, or valid-no-op probe shows its true state instead of a leftover "succeeded"/"failed."
- **"Completed — no applicable data" is not a failure.** When CFBD returns a valid empty partition (postseason scores before bowls are published, a week with no games), the refresh resolves as a **no-op**: nothing is written, prior-good data is preserved, and the card shows a muted "no applicable data" — not a red failure. ESPN is no longer an automatic fallback, so a genuine CFBD failure is surfaced (prior-good retained) rather than masked by a second provider.
- **An empty schedule is classified before it is stored.** A schedule refresh that returns zero games is judged _before_ any durable/process-cache write: if a populated schedule is already cached, the empty result is **rejected** as an unexpected replacement (prior-good schedule retained, refresh recorded as failed) rather than committed and then labelled a no-op; only a genuinely inapplicable/unpublished empty (e.g. postseason before bowls, a future season) resolves as a no-op. A committed empty schedule that then reported "no-op" (preserving stale success metadata while the cache was emptied) is the exact contradiction this prevents. Classifying that empty requires reading the prior durable schedule; if **that read itself fails** (a transient app-state outage) neither branch is safe, so both the authorized schedule route and the season-transition cron record the open attempt as a **failure** (`schedule-prior-cache-read-failed`, prior-good retained, the cron does not transition off the unverifiable probe) rather than leaving the attempt stranded `in-progress` — a read failure is an operational failure, never a classification result.
- **Game-stats and rankings empties are classified too.** A game-stats refresh (cron or manual) flows through the single ingestion path (`ingestGameStatsPartitionResponse`) and the single outcome interpreter (`interpretGameStatsRefreshOutcome`), never a standalone payload classifier: an exact empty CFBD array is an `empty-response` **no-op** (nothing is written and last-success is not advanced — a written empty would read as covered yet still be retried); a top-level payload that is not an array is an `invalid-payload` **failure**; and a nonempty payload from which no persistable observations parse is a `no-persistable-observations` **failure** (prior-good retained). A payload that reaches the H2 durable merge is interpreted into ONE of four kinds — `success`, `partial`, `no-op`, or `failure` — via a stable reason: `written-clean` → success; `written-mixed`/`partially-merged` → partial; `unchanged-clean`/`stale-clean` → no-op; `unchanged-mixed`/`stale-mixed`/`conflict`/`unavailable`/`indeterminate` → failure. (Interpreter kinds, durable-merge outcomes, and reasons are distinct layers, not interchangeable labels.) Conferences behave the same on their authorized refresh: a non-array 200 payload is a `conferences-invalid-payload` failure and an empty (or nonempty-normalizing-to-zero-usable) payload is a `conferences-no-usable-rows` failure — reference data does not legitimately vanish, so neither commits an empty cache or records success (prior-good retained, the admin action reports the bundled fallback as a failure). Rankings behave the same, and validate each partition **independently before combining**: a nonempty regular _or_ postseason partition that normalizes to zero usable weeks is schema drift (`rankings-partition-schema-drift`, prior-good retained) — a healthy partition can never mask a drifted one, and drift is never mistaken for valid absence. A genuinely empty (raw) rankings response is a pre-poll no-op when no prior-good rankings exist, and an unexpected empty replacement (`rankings-empty-replacement-rejected`) that retains prior-good when they do. **Since PLATFORM-086E2A every rankings refresh flows through the ONE shared authority** (`refreshSeasonRankings`; PLATFORM-086E2B adds the publication-aware automatic caller — see "Rankings publication cron logging" below; ACTIVE since the §8j activation, 2026-07-30): its scoped year-rollup status is recorded exactly once per attempt from the typed result — `written-clean`/`unchanged-clean` record success only after the confirmed durable commit, `empty-response`/`stale-observation` record a no-op that never advances last-success, and the new truthful failure codes include `rankings-partition-incomplete` (an incoming aggregate would lose previously cached weeks or previously populated poll sources — prior-good retained and served stale-marked) and `rankings-durable-commit-failed`. A concurrent same-year manual refresh now returns HTTP `409 {"error":"rankings-refresh-in-progress"}` with no provider call and no status attempt, and rankings data is marked stale on the **8-day** weekly-cadence horizon (never the retired 6-hour process TTL).
- **Disrupted-only slates never poll.** The game-stats cron's kickoff-window polling (`pollingTarget.ts`) only considers stat-applicable (non-disrupted) games, so a week of only canceled/postponed/suspended/delayed games yields no polling target (it can never produce usable stats) and raises no missing-stats warning.
- **Odds quota freshness ≠ odds-data freshness.** The panel's quota display reads durable odds usage on every load, but the odds **staleness diagnostic** derives from the selected season's **canonical** `odds-cache` entry (`defaultOddsCacheKey`), not that quota timestamp and not any filtered-query variant — a failed 402/429, another season's request, or a filtered markets/bookmakers refresh can move quota or a sibling cache key without refreshing the served snapshot, and must not make stale odds look fresh.
- **Manual score refresh is ONE aggregate action, server-authoritative on applicability.** The scores refresh issues a single aggregate request under **one** `scores` attempt, so the whole operator action has a single truthful status owner — a partition's success or valid no-op can **never** erase another partition's failure. The **server** derives the applicable partitions cache-only from the requested year's schedule (`getApplicableScoreSeasonTypes` — regular, plus postseason once bowls are scheduled; 7th review), so a mid-regular-season refresh does not fire a doomed postseason request **even if the client omits or mis-sends the partition list**, and the action does not report failure merely because an inapplicable partition was skipped or validly empty. A client `seasonTypes` list is honored only as an explicit targeted repair (e.g. postseason-only); an absent/invalid list falls back to server-derived applicability. If any applicable partition fails, the aggregate reports failure with the failed partitions listed even when another partition committed (`partialFailure` set, prior-good last-success preserved).
- **The status feed is isolated to the currently selected year.** The panel guards `/api/admin/provider-status` loads with a monotonic request sequence + an `AbortController` and validates BOTH the echoed `year` AND the currently selected year (`shouldApplyStatusResponse` = `isCurrentStatusResponse` + a live `yearRef` check), so a response for a since-abandoned year cannot replace, error, or re-spinner the newer feed even if it echoes its own matching year. A stale manual-refresh or settings callback captured under year A cannot start an old-year load or abort year B's active request; `load()` always targets the live selection. A settings mutation reloads whatever year is selected **at completion**; a manual dataset refresh reloads only if its captured year is still selected. Manual-refresh action state (pending/success/failure/message) is keyed by `${year}:${dataset}` (`manualActionKey`), so a 2025 "Refresh complete" never appears on a 2026 card and no year-A spinner shows on year B; **game-stats** extends that identity to `${year}:game-stats:${week}:${seasonType}`, so a Week 1 regular result or spinner never shows beside Week 2 or postseason (which were never fetched). Superseded/aborted/unmounted loads surface no stale error or spinner.
- **Dataset cards render only a verified selected-year feed.** Cards, diagnostics, the global-pause control, and the odds quota render **only** from a successful feed whose `feed.year` equals the selected year (`panelFeedRenderState`). There are no synthesized placeholder "no history" rows: while the selected year's feed is loading the panel shows _"Loading provider status for {year}…"_, and if the request fails with no valid feed it shows _"Provider status unavailable for {year}"_ (with the error). Changing years hides the previous year's cards immediately rather than showing them under the new year until (or unless) the new load lands. The CFBD quota is an independent per-mount read and stays visible regardless.
- **CFBD quota is reconciled once and shared.** The CFBD quota is normalized by a single shared model (`normalizeProviderQuota` in `src/lib/api/providerQuota.ts`) consumed by BOTH the Provider Data Status panel and the legacy **API Usage** panel, so they can never disagree or render an impossible combination (e.g. "5,000 remaining of 3,000"). The canonical CFBD **Tier 1 monthly limit is 5,000 calls** (single source of truth `CFBD_LIMIT_BY_TIER`; a stale 3,000 produced the impossible "0 used / 5,000 remaining / 3,000 limit" display). The normalized summary satisfies `used + remaining = limit`; when the raw provider fields are internally inconsistent it falls back to the canonical Tier limit and marks the raw observation inconsistent (retained as diagnostic detail), and when nothing trustworthy exists it reports "quota status unavailable" rather than an impossible number. The legacy API Usage panel shows the raw provider fields only as clearly-labeled diagnostic detail, never as the authoritative quota.
- **"Global provider pause" is a pause state, not an automation status.** The global control reads **Global provider pause: Off / On** (persisted `provider-refresh-settings.globalPause`), not the old "Global automatic refresh — Active". Off means noncritical automatic provider polling is allowed; On pauses it. Manual admin refresh and lifecycle-critical OPERATIONS — the season transition/rollover crons and the weekly cron's postseason-boundary schedule maintenance — always keep running (they never consult `isAutoRefreshAllowed`, which since PLATFORM-086E1B strictly evaluates the settings with no dataset-level bypass). The action buttons remain "Pause automation" / "Resume automation"; the wording change alters no persisted setting or cron behavior.
- **Manual game-stats repair is season-type-aware.** The game-stats card has both a week and a season-type (regular/postseason) selector — a postseason repair targets the postseason cache key rather than defaulting to regular.
- **Fallback is not success.** A manual refresh whose route degraded to bundled/prior-good/stale fallback is reported as "Provider refresh failed; fallback data is still serving," not as complete. The shared interpreter treats `meta.fallbackUsed` / `meta.source: 'local_snapshot'` (the conferences route on a provider error) **and** `meta.stale` / `meta.rebuildRequired` (the rankings loader returns HTTP 200 with these when it rejects an empty/drifted replacement and keeps serving prior-good rankings) as failure — none of them read as "Refresh complete."
- **Odds quota is a fresh durable read.** The panel reads durable odds usage on every load (not a process memo), so a refresh on another instance is reflected rather than showing an indefinitely stale remaining/quota.
- **Controls are interactive only when they do something.** A per-dataset auto-refresh toggle is interactive only for datasets whose setting a live job consumes today — game-stats, scores (live-score cron), odds (Odds cron), **schedule** (the PLATFORM-086E1B weekly cron: Off pauses ORDINARY weekly maintenance only; the lifecycle-critical season transition and postseason-boundary maintenance remain exempt regardless of the toggle), and **rankings** (the PLATFORM-086E2B publication cron: ALL rankings automation is noncritical, so Off — or the global pause — pauses every automatic rankings refresh; the authorized manual refresh stays available and ungated). The one remaining planned dataset (conferences) shows read-only "control not active yet." The settings API likewise rejects toggling a dataset with no setting-consuming job. This keeps the panel from implying a runtime effect that does not exist yet.
- **Failed pause/toggle mutations surface beside their control (PLATFORM-086I).** When the **global pause** or an **interactive** dataset's auto-refresh **toggle** POST fails, the panel renders a compact red `role="alert"` region directly beneath that control (associated with it via a conditional `aria-describedby` to a stable id — `provider-global-pause-error` / `provider-toggle-<dataset>-error`) showing the stored error after a short control-specific prefix. Because the panel is authoritative-state, not optimistic, the confirmed On/Off and the checkbox are left untouched on failure — the setting only changes once a successful POST is reloaded from the feed. Retrying sets the action to `loading`, which clears the stale alert while the request is pending, and a successful retry reloads the selected year. Only a setting-consumed (`interactive`) dataset can raise a toggle alert, so it appears on the Game Stats card only today; the manual-refresh feedback path (`Refresh failed:` / `Refresh complete.`) is separate and unchanged.

### Weekly schedule-maintenance scheduler execution logging (PLATFORM-086E1B)

**PLATFORM-086E1B** (corrected by **E1B1**) adds the same runtime-event contract to the weekly schedule cron: `GET /api/cron/schedule-refresh` emits exactly ONE secret-safe, single-line JSON event per invocation — `console.log(JSON.stringify(event))`, observed in **Vercel Runtime Logs** — for auth failures, skips, every per-year outcome, and unexpected exceptions alike. The route is **ACTIVE — `turfwar-schedule-weekly` (Tuesdays 12:00 UTC) was provisioned by the runbook §8h sequence (2026-07-29)**; while the 2026 leagues remain in preseason, deliveries defer provider work truthfully (`skipped / season-transition-owner`) to the daily season-transition cron. Each delivery targets every distinct `season` AND `preseason` year cache-only (league registry `status.year`, ascending; any `season` league owns a mixed year — one execution under the active-season policy; `offseason` excluded; **the demo league is filtered out per league, before ownership is resolved** — PLATFORM-086F2H1T3, so it can neither contribute a year nor change which policy a shared year runs under) and delegates each allowed year ONCE to the E1A full-season authority. Gating is **operation-aware** — the ordinary operations (`ordinary-maintenance`, and E1B1's cache-armed early-preseason `preseason-maintenance`) honor `isAutoRefreshAllowed('schedule')` (global pause + the Schedule toggle), while **postseason-boundary** maintenance (from 7 days before the year's latest regular-season kickoff) is lifecycle-critical and never consults settings, so an operator pause can never starve the season-rollover boundary. A preseason year whose probe is unarmed — or that is inside the final seven days before the first kickoff — is an intentional provider-free deferral to the DAILY season-transition cron (`skipped / season-transition-owner`, mirroring transition's exact `shouldFetch` boundary), never a failure.

The event carries ONLY this allowlisted shape (`src/lib/schedule/cronExecutionLog.ts`) — never a request/response object, thrown error, schedule item, provider payload, probe record, registry row, URL, credential, or header:

- `event`: always `"schedule-refresh-cron"`.
- `result`: `skipped` | `success` | `partial` | `no-op` | `failure` — aggregated over the year entries (no entries or all-skipped → `skipped`; a failure plus a non-failure among the non-skipped → `partial`; all non-skipped failed → `failure`; ≥1 success and no failure → `success`; otherwise `no-op`). Neither a skipped/gated ordinary year NOR a transition-owned deferral ever makes a successful sibling year `partial`.
- `reason`: `cron-secret-not-configured` / `cron-authorization-invalid` (auth); `no-maintenance-target` (no `season` or `preseason` league); `no-automatic-maintenance-target` (active leagues exist but every one is the demo league, which is manual-only for weekly maintenance — PLATFORM-086F2H1T3); `registry-malformed` (the registry record EXISTS but does not hold a league array — PLATFORM-086F2H1R2; **HTTP 200 here**, unlike the season-transition cron's 500 for the same condition, because this route answers every controlled outcome with 200 — see the HTTP note below); `unusable-lifecycle-year` (every surviving production candidate carried a structurally invalid `status.year`, so the run has no usable target — F2H1R2); `season-transition-owner` / `automation-paused-or-disabled` / `canonical-context-unavailable` / `settings-unavailable` (uniform deferral/gated/context/settings outcomes); `year-results` (mixed or executed per-year outcomes); `unexpected-error` (pessimistic default).
- `invalidLifecycleTargets` (PLATFORM-086F2H1R2): a run-level count of PRODUCTION candidates refused for a structurally invalid `status.year`. **Counts only — never a slug and never the unusable value.** Run-level rather than per-year because a refused candidate has no usable year to file it under, and it counts LEAGUES, not distinct years: three records sharing one bad year count three. A DEMO record is never counted — the demo exclusion runs first, so a malformed demo record still reports `no-automatic-maintenance-target`. Neither are `offseason` or status-less production records: they were never candidates. Present on the response body, this event, and the receipt target alike; a legacy receipt that predates the field normalizes to `0`.
- `years[]`: one entry per candidate year — `year`, `operation` (`preseason-maintenance` | `ordinary-maintenance` | `postseason-boundary` | `null` when deferred/context-unavailable), `result` (`skipped` | `success` | `no-op` | `failure`), `reason` (the E1A refresh reason, or `season-transition-owner` / `automation-paused-or-disabled` / `canonical-context-unavailable` / `settings-unavailable`), `providerCallAttempted` (the E1A instrumentation — false for every pre-provider exit, true from the fetch pair onward including failures), `rowsReceived`, `rowsCommitted`, `dataChanged`. A refused candidate produces NO entry here.
- `durationMs`: whole-invocation duration, a nonnegative integer.

Exact behavior to know when reading it:

- **Controlled operational failures are HTTP 200, by design.** Only authentication returns `401`. A registry/context/settings failure, a gated skip, and every E1A outcome return `200` with the truthful body/event — QStash delivered the message and the app processed it; monitor the event `result`/`reason`, not the HTTP status (QStash retries are 0 regardless).
- **A skipped, deferred, or context-unavailable year spends nothing**: no provider-refresh attempt is begun, no provider request is made (`providerCallAttempted: false`), and E1A is not invoked. A `season-transition-owner` deferral additionally consults NO settings and touches NO postseason latch. Lease contention inside E1A surfaces as a truthful `no-op / refresh-in-progress`.
- **A settings-store failure blocks ONLY the ordinary operations** (`failure / settings-unavailable` for `ordinary-maintenance` AND `preseason-maintenance`); postseason-boundary years proceed without reading settings at all — a mixed invocation can be `partial` (critical success + ordinary settings failure).
- **Preseason never touches the postseason latch** (`schedule-weekly-control/<year>` is read/written only for `season`-owned years), and a genuine store read failure or an armed-probe/missing-schedule contradiction is `canonical-context-unavailable` — never silently converted into a transition deferral.
- **A successful `preseason-maintenance` refresh re-derives the probe's `firstGameDate`** from the committed schedule (preserving `baseCachedAt`, mirroring the manual full-year refresh's probe update, best-effort) — so if a weekly refresh commits an EARLIER first game, the season-transition handoff window follows the refreshed schedule instead of a stale probe.
- **Duplicate/overlapping deliveries are safe**: E1A's durable per-year lease plus observation-ordered commit make a QStash at-least-once redelivery a truthful `no-op` (`refresh-in-progress` or `stale-observation`), never a duplicate provider spend or an older overwrite.
- **A corrupt registry no longer reads as an empty one (PLATFORM-086F2H1R2).** The route reads the registry CONTAINER through `readLeagueRegistry()`, so a present-but-non-array record reports `failure / registry-malformed` before any schedule read, probe, latch, settings read, provider request, or presentation refresh — instead of `no-maintenance-target`, which asserts no active league exists when the registry holding them is unreadable as a list. A genuine store read failure remains `failure / canonical-context-unavailable` (it throws, and unavailability stays distinct from corruption). That catch also covers a corrupt RECORD inside an otherwise valid container: the array is typed `League[]`, but nothing validates each element, so a non-object member throws on property access.
- **A refused target never bills anything, and the refusal survives a later throw.** A production league with a structurally invalid `status.year` (missing, string, fractional, unsafe-integer, or pre-1869) contributes no year key, no owner precedence, no per-year entry, no `schedule/<raw>-all-all` read, no boundary-latch or probe operation, no settings decision, no billed E1A refresh, and no presentation refresh. Before F2H1R2 an unusable year reached CFBD as `year=undefined`. Refusals counted before a later league throws still reach the response, event, and receipt — the count is not discarded by the failure path.
- **Aggregation when refusals coexist with executed years** (the R1-approved table, identical on both jobs): no refusals → the normal aggregate, unchanged; refusals with no executed years → `failure / unusable-lifecycle-year`; refusals plus executed years → keep the executed years' uniform reason (`year-results` only when they genuinely disagree) and classify `partial` when their aggregate is `success` or `partial`, else `failure`. The reason is never overwritten by the refusal, because the receipt's year entries carry no reason field — overwriting would erase the only durable record of what those years did. One consequence worth knowing when reading a run: `unusable-lifecycle-year` is unreachable as a REASON whenever any valid year also executed; only the count reports the refusal there.

What to know when reading it:

See `docs/next-tasks.md` item (p).
- **A completed publication window never spends again.** A redelivered/duplicate heartbeat for a completed key is `skipped / publication-window-complete` with zero `/info` probes and zero rankings requests — the durable window control plus E2A's per-year lease + observation ordering make at-least-once delivery safe end to end.
- **A skipped year spends nothing**: `not-a-heartbeat-slot` (the delivery instant is outside the fixed 04:00/22:00 minute-zero slots), `no-window-due`, and `publication-window-complete` years perform no claim (or only a read), no `/info` probe, no provider request, and begin no provider-refresh attempt.
- **Delayed deliveries skip truthfully.** The window classifier evaluates the single route-entry instant against minute-exact slots, so a QStash delivery delayed past `hh:00` (queueing, cold start, mid-deploy) yields `not-a-heartbeat-slot` and the day's window waits for its next occurrence — an accepted operational property (retries are 0), not a defect; persistent occurrences of this reason warrant checking QStash delivery latency.
- **`quotaChecked` means the `/info` probe ran; `providerCallAttempted` is E2A's truth** — a quota refusal has `quotaChecked: true, providerCallAttempted: false` and never invokes the authority. Each due year gets its own FRESH probe (sequential execution re-evaluates the reserve before every spend).

### Scheduler execution receipts (PLATFORM-086F2E1 / F2E2A)

**PLATFORM-086F2E1** adds a durable, latest-only **execution receipt** for each of the five QStash-triggered cron routes (`live-scores`, `game-stats`, `odds`, `schedule-refresh`, `rankings`); **PLATFORM-086F2E2A** extends the same authority to the two Vercel-native lifecycle crons (`season-transition`, `season-rollover`) and — since those two routes previously emitted NO app-side execution event — also adds their runtime execution-log events. All seven receipts are stored under `scheduler-execution-status/<job>` (see [storage-and-caching.md](../architecture/storage-and-caching.md) → "Scheduler execution receipts"). Unlike the runtime execution-log events — which stay the detailed, per-invocation Vercel Runtime Logs surface, **including authentication failures** — the receipt is a **durable cache-only** record that proves an _authenticated_ scheduled delivery reached the application: it is written ONLY after `verifyCronSecret` returns `ok` (an auth failure never creates or advances a receipt), carries the route tracker's verbatim `result`/`reason`, `providerCallAttempted`, and a bounded target, and is committed with monotonic latest-only ordering so an older overlapping completion can never overwrite a newer delivery. The receipt never replaces or changes the runtime event, and receipt-store failures are swallowed (they never alter a cron response, provider behavior, cadence, or the execution-log events).

**What to know when reading it today:**

- **A cache-only SERVER reader now exists (F2E2B); there is still no UI.** `src/lib/server/schedulerDeliveryHealth.ts` reads the scope once and returns seven state-bearing rows — each with its fixed UTC policy, the `requiredStartedAt` slot, a `deliveryState` (`on-time` | `late` | `missing` | `invalid` | `unavailable`), and the safely-parsed receipt. Delivery timeliness is the receipt's `startedAt` versus the most recent fixed UTC slot at/before (`now − grace`), never the execution `result`/`reason`/provider flag (a timely skip/no-op/failure is still `on-time`) and never the durable `updatedAt`. It performs no provider call or write and has **no route or UI** — **F2F** builds the consolidated System Health view model (issue codes, severity, repair links) that consumes this reader, and **F2G** owns the UI. A `missing` or `late` receipt does NOT identify a root cause: it cannot distinguish a scheduler failure from non-provisioning or a best-effort receipt-store failure. Until F2F/F2G, inspect a receipt directly via the durable store (`scheduler-execution-status/<job>`).
- **It is separate from `provider-refresh-status`.** The receipt describes scheduler _delivery_ (did an authenticated invocation run, when, with what result and bounded target); `provider-refresh-status` describes provider-_data_ attempts and durable commits. A skip/no-target receipt is a healthy delivery and never fabricates a provider attempt.
- **`source` is not a cryptographic provenance claim.** It is DERIVED from the job (never accepted from a caller) and names the configured scheduler owner — `qstash` for the five QStash jobs, `vercel-cron` for the two lifecycle crons. It marks an authenticated application-boundary execution; F2E2A introduces no QStash signature verification and inspects/persists no request headers.

### Lifecycle scheduler execution logging (PLATFORM-086F2E2A)

**PLATFORM-086F2E2A** adds the runtime-event contract the five QStash crons already had to the two Vercel-native lifecycle crons — `GET /api/cron/season-transition` and `GET /api/cron/season-rollover` — which before this shipped emitted no app-side execution event (their auth failures were visible only in platform request logs). Each now emits exactly ONE secret-safe, single-line JSON event per invocation from a single outer `finally` (Vercel Runtime Logs) — auth failures, skips, every per-year outcome, and unexpected exceptions alike — owned by `src/lib/lifecycleCronExecutionLog.ts`. Neither event ever serializes a request/response object, thrown error/message/stack, league record or slug, schedule row, archive, provider payload, environment value, URL, credential, or header. Emission is best-effort (a serialization/console failure never changes the response or masks a throw), and the new receipt is scheduled only after successful authentication.

- **`event: 'season-transition-cron'`** — `result` (`skipped` | `success` | `partial` | `no-op` | `failure` | `in-progress`), aggregated over the per-year entries; `reason` is the uniform per-year reason or `year-results`, with route-level literals `cron-secret-not-configured` / `cron-authorization-invalid` (auth), `no-preseason-leagues`, `no-automatic-preseason-leagues` (preseason leagues exist but every one is the demo league, which is manual-only — PLATFORM-086F2H1T2), `registry-unavailable`, `registry-malformed` (the registry record EXISTS but does not hold a league array — distinct from `registry-unavailable`, where the store read itself failed; HTTP 500, no probe/provider/lifecycle work — PLATFORM-086F2H1R1), `unusable-lifecycle-year` (every production preseason candidate carried a structurally invalid `status.year`; HTTP 200, a controlled data-integrity refusal — F2H1R1), and `unexpected-error`. A run-level **`invalidLifecycleTargets`** count appears on the response, the event, and the receipt target: how many PRODUCTION candidates were refused for an unusable year. Counts only — never a slug and never the unusable value. It is run-level rather than per-year because a refused candidate has no usable year to file it under. A DEMO record is never counted: the demo exclusion is applied first, so a malformed demo record still reports `no-automatic-preseason-leagues`. When refusals coexist with executed years the reason keeps naming the executed years (the count carries the refusal), and the result is `partial` only when their aggregate is `success` or `partial`, else `failure`. Each `years[]` entry carries `year`, `result`, `reason` (a control reason — `probe-state-unavailable`, `probe-write-failed`, `lifecycle-write-failed`, `refresh-not-due`, `season-transitioned` — or the exact E1A `FullSeasonScheduleRefreshReason`), `scheduleRefreshReason` (the exact E1A reason when a refresh ran, else null), `providerCallAttempted` (E1A's field, copied verbatim), `targetLeagues`, `probed`, `cached`, `transitionedLeagues`, and `failedSeasonTypes`. Controlled operational failures keep their existing HTTP status (a registry read failure and a genuine schedule store outage are 500 exactly as before; data/partition failures stay 200); only lifecycle/provider truth drives the event.
- **`event: 'season-rollover-cron'`** — `result` aggregated the same way; `reason` uniform-or-`year-results` with route-level `cron-secret-not-configured` / `cron-authorization-invalid`, `no-season-leagues`, `no-automatic-season-leagues` (leagues ARE in season but every one is the demo league, which is excluded from automatic rollover — PLATFORM-086F2H2B; this is the DEFAULT post-reset demo state, so it is the ordinary quiet-run reason whenever production is not in season). **Zero-target precedence:** `registry-malformed` → `unusable-lifecycle-year` (every production candidate refused) → `no-automatic-season-leagues` (an ACTIVE demo was excluded and nothing else was in season) → `no-season-leagues` (genuinely nothing in season). The demo flag is set only when the demo league is itself in `season`, so an offseason or status-less demo never displaces the honest reason, and it is decided BEFORE year validation, so a demo carrying an unusable year stays a demo exclusion rather than being counted as a refused production target. `registry-unavailable`, `registry-malformed` (the registry record EXISTS but does not hold a league array — distinct from `registry-unavailable`, where the store read itself failed; **HTTP 500**, refused before any championship resolution, archive build/save, lifecycle write, standings invalidation, or suppression cleanup — PLATFORM-086F2H1R4), `unusable-lifecycle-year` (every surviving production candidate carried a structurally invalid `status.year`; HTTP 200 — a known asymmetry with the 500 above, inherited from R1 and recorded for a campaign decision), and `unexpected-error`. A run-level **`invalidLifecycleTargets`** count appears on every AUTHENTICATED response, the event, and the receipt target: production league RECORDS refused for an unusable `status.year` (counts only — never a slug or the unusable value; three records sharing one bad year count three). A demo record is never counted, and neither are non-`season` records. A refusal decided at WRITE time counts too: `completeSeasonRollover` validates independently inside its transaction, on BOTH the stored and requested year and BEFORE the exact-year comparison, so a corrupt record reports `unusable-target-year` (repair the record) rather than `not-in-target-season` (another actor moved it) — two different remedies that must not be conflated. **Rollover is the one registry consumer that WRITES durable data derived from the year** — `saveSeasonArchive` keys on `String(archive.year)` with no TTL, and the written `{ state: 'offseason' }` status carries no year, so the top-level `league.year` becomes the only surviving record and feeds `resolveOperationalSeasonYear`. Each `years[]` entry carries `year`, `result`, `reason` (`read-failed`, `rollover-complete`, `rollover-partial`, `rollover-failed`, or the exact `ChampionshipRolloverSkipReason`), `providerCallAttempted` (**always `false`** — rollover is cache-only), `targetLeagues`, `rolledOverLeagues`, and `suppressionCleared`. Archive-first per-league failure isolation and the guarded conditional transition are unchanged; a per-league archive/status failure makes its year `partial` (some rolled) or `failure` (none rolled) without changing the existing response body. **Standings invalidation and suppression clearing were decoupled by PLATFORM-086F2H2B.** Invalidation is now reported separately from the lifecycle write — a `revalidateTag` throw on a league that DID roll reads `standings invalidation failed after a successful rollover`, not `status write failed`, because the remedy for a stale cache is not the remedy for a failed transition. It no longer skips the suppression clear either: the two shared one catch, so a cache fault used to leave the outgoing season's DURABLE insights suppression in place. Clearing still requires archive AND status success, and still never fails the rollover. An invalidation failure keeps its year `partial` (the league rolled, but the run reports an error).

### System Health read model (PLATFORM-086F2F)

**PLATFORM-086F2F** adds the server-side view model `buildSystemHealthViewModel` (`src/lib/server/systemHealth.ts`) that F2G will render on `/admin/diagnostics`. It is server-only — no route, UI, mutation, durable schema change, or provider/scheduler behavior change — and keeps **six independent facts distinct** rather than reproducing the old panel's conflations:

- **Scheduler delivery** — did an authenticated invocation arrive on time (from the F2E2B reader) — vs **scheduler execution outcome** — what the parsed receipt reported. A late-but-successful run raises a delivery-late issue but no execution fault; an on-time failed run raises an execution fault but no delivery issue.
- **Canonical data health** — cache/evidence freshness from `providerDataDiagnostics` (unchanged freshness policies: schedule/rankings 8-day, odds 2-day in the active-season window, scores terminal-coverage, game-stats participant-verified evidence) — never inferred from provider-status timestamps.
- **Automation gates** — pause/disable state, surfaced only as INFORMATIONAL issues that never demote a missing/late delivery and never make `overallState` degraded by themselves.
- **Quota** — one deliberate cached CFBD observation against the 1,007 reserve; Odds against the real 53-credit automatic threshold.
- **Storage** — configuration mode (never a "healthy database" claim from mode alone; the filesystem path is never serialized).

Two axes stay separate (seven scheduler jobs, six provider datasets — not 1:1). **Stable issue vocabulary:** every issue carries a machine-readable `code`, a `severity` (`critical`/`warning`/`info`), a `subject` (`global`/`job`/`dataset`), a safe STATIC `explanation` (never a copied diagnostic message or thrown-error text), and a **nullable** `repair` — Data Maintenance (`/admin/data/cache`), Season Management (`/admin/season`), Team Identity (`/admin/aliases`), or `null` when nothing in-app repairs it (missing/late delivery, quota exhaustion, storage misconfiguration, unavailable observability reads, manual-only game-stat evidence). Diagnostics gain matching stable `ProviderDiagnosticCode`s; a game-stat identity mismatch routes to Team Identity while duplicate/conflict routes to Data Maintenance. Issue order is deterministic (severity → axis → canonical job/dataset order → subject → code); `overallState` is `critical` / `degraded` / `healthy` with info-only staying `healthy`. Subsystem read failures degrade only their own fact to `unavailable` (surfaced, e.g. `provider-status-unavailable`, `scheduler-delivery-unavailable`, `data-diagnostics-unavailable`, `automation-settings-unavailable`) without leaking raw errors or failing the whole model. F2G renders it.

### Lifecycle-integrity issue (PLATFORM-086F2H3B2)

**PLATFORM-086F2H3B2** adds one System Health issue for stored league records that automation refused, closing a follow-up carried since PLATFORM-086F2H1R3.

- **`lifecycle-data-unusable`** — severity `warning`, axis `global`, subject id `lifecycle-integrity`. Title: "Production lifecycle data is unusable". Explanation: "Automatic processing refused production lifecycle data. Some processing may be incomplete." followed by the reporting job names.
- **Trigger:** any parsed scheduler receipt whose target reports `invalidLifecycleTargets > 0`. It is derived from the receipt TARGET and **never from the run's `result`** — a valid target can succeed while another production record is refused, so a `success`, `partial`, `no-op`, or `skipped` run can still carry refusals. It is ADDITIVE to `scheduler-execution-failed` / `-partial`, never a replacement; a wholly refused run raises both, and they answer different questions (what the run did vs. what the stored data is).
- **ONE combined issue, and no number.** Counts are per JOB and per RUN and count RECORDS, and the same corrupt league is counted independently by up to four jobs (season-transition while it is preseason; schedule-refresh, rankings, and season-rollover while it is in season). Summing multiplies one league into several, a maximum compares runs from different times, and a deduplicated league count is not derivable at all because a receipt carries counts and never a slug. The issue therefore names the reporting JOBS and states no figure. To see the per-job counts, open that job's row on System Health — the target summary still shows `· N unusable lifecycle target(s)`.
- **A job with no readable receipt contributes nothing.** `missing` / `invalid` / `unavailable` delivery leaves no parsed receipt, and a run that reported nothing cannot be assumed to have reported a refusal.
- **Where it appears on the dashboard.** It belongs to no stoplight tile — lifecycle integrity is not a delivery fact, a provider fact, a gate, a quota, or storage — so it is claimed explicitly and kept out of every section, and folded into **Overall** instead. The visible consequence is deliberate: the five section tiles stay green while **Overall** shows "Attention needed", and the issue carries its own title and explanation in the Actionable Issues list below. Without that explicit claim it would fall into **Provider data**, whose predicate is residual, and would both misattribute a league-registry fault to provider data AND displace a genuine provider fault from that tile's single detail line.
- **Clearing:** when no parsed receipt reports a positive count. A STALE receipt therefore holds the warning up until that job runs again. This is deliberate — the stored record stays corrupt until it is repaired, and the last thing any job observed is the best available evidence.
- **There is no repair link, and that is not an omission.** No supported operation writes a lifecycle status or year onto a PRODUCTION record: `updateLeague` throws on `year`/`status`, `PATCH /api/admin/leagues/[slug]` answers 409 for both (`league-year-lifecycle-managed` / `league-status-lifecycle-managed`), the Settings "Season Year" field is read-only, and `resetTestLeagueLifecycle` takes no slug and reaches only the demo league. **Operator response today:** identify the offending record from the durable registry (`leagues/registry`) and repair it out of band; a supported recovery operation is PLATFORM-087's and is unscheduled.

### System Health UI (PLATFORM-086F2G)

**PLATFORM-086F2G** turns `/admin/diagnostics` into **System Health**, a current-status dashboard rendering the F2F model. Operator-visible behavior:

- **Read it in seconds:** a stoplight overview (Overall, Scheduler delivery, Provider data, Automation, Provider quota, Durable storage) is the primary signal — green healthy/current, yellow degraded/stale/late/unavailable, red critical/failed/misconfigured, gray intentionally paused/awaiting — each with a text state label (never color alone). The Overall tile is a rollup that never contradicts a section tile.
- **Actionable issues** sit directly below, in the model's deterministic order; a repair link appears only when there is a real repair surface (Data Maintenance / Team Identity) — otherwise none. **Since F2H4 a LIFECYCLE scheduler fault has no repair link:** it pointed at Season Management, which could not repair a lifecycle fault and has been retired.
- **Delivery vs execution are separate** per scheduler row: the delivery stoplight is timeliness; the execution column is the receipt's result, and a missing / invalid / unavailable receipt reads distinctly (never all "no receipt"). **Provider rows** keep cache freshness, latest refresh outcome, and automation state as separate facts; the timestamp is the latest ATTEMPT (a preserved prior success shows separately). Row-level "Details" disclose forensic metadata (source, cadence, target, scope key, sanitized error code/status, failed partitions, rows, duration).
- **Quota** shows CFBD headroom against the 1,007 reserve and Odds against the 53-credit threshold with snapshot age; **storage** reports configuration only (never a database-liveness claim). **Automation** distinguishes a global pause from a per-dataset "Partially disabled" and notes that lifecycle-critical Schedule operations stay exempt.
- **Refresh view** rebuilds the server model; there is **no browser polling**. The only mutations are the global pause and per-dataset automation toggles (`POST /api/admin/provider-status`, unchanged), with attempt-scoped accessible feedback. Only the provider-data section is season-scoped (server-resolved operational season, no `?year=` selection) — and since PLATFORM-086F2H1T5 that season is resolved from PRODUCTION leagues only: the demo league neither contributes a year nor changes the selection, in either the active-lifecycle branch or the stored-year fallback. Note the year is not confined to that section: the issues and freshness derived from the year-scoped inputs feed `overallState`, `issueCounts`, and the headline Overall tile, and a wrong year can both fabricate faults for the year it names and hide genuine provider-refresh failures for the year it displaced. The scheduler/automation/quota/storage FACTS themselves are current/global. The old incremental Provider/Usage/Storage panels are retired.

### Odds refresh authority (PLATFORM-086C1, DORMANT — C2-ready)

**PLATFORM-086C1** made the Odds refresh/write system concurrency-safe before automatic Odds polling exists. It changes how the authorized manual `/api/odds?refresh=1` refresh and the public canonical closing-line maintenance commit, and adds dormant infrastructure the FUTURE PLATFORM-086C2 cron will consume. **Automatic Odds polling is NOT active** — there is no `/api/cron/odds`, no QStash schedule, and the `odds` provider descriptor stays `hasActiveAutomation: false` / `autoRefreshSettingConsumed: false`.

What to know when reading Odds behavior:

- **Shared refresh lease (duplicate-spend protection).** One durable record per exact season-scoped Odds target (`odds-refresh-control/<seasonScopedKey>` in AppStateStore) carries a `crypto.randomUUID` lease token (5-minute duration, reclaimable once expired), a `lastCompletedCheckAt`, and the durable automatic-backoff counters. Acquisition/finalization run inside `withAppStateKeyTransaction`, so overlapping refreshes serialize; finalization is token-checked, so an older holder can never clear a newer lease. A billed provider/payload/commit failure advances a durable **1h → 2h → 6h → 12h → 24h** backoff (`automaticNotBefore`); a success or valid no-op resets it. Manual refresh **ignores** the backoff but still needs the lease; missing credentials, quota refusal, and context failure are not billed failures.
- **Intentional concurrent-manual `409`.** A manual `refresh=1` that arrives while a nonexpired lease is held returns HTTP **`409`** with stable code **`odds-refresh-in-progress`** — **no** provider call and **no** fabricated provider-refresh attempt. This is the one intentional new manual behavior; every other manual/public response shape is unchanged.
- **Atomic canonical write + observation ordering.** For the canonical/default target the raw odds cache (`odds-cache/<seasonScopedKey>`) and the durable per-game store (`durable-odds:<season>/store`) commit in ONE multi-key advisory transaction (rooted at the store, `odds-cache` locked second). Process caches and provider-refresh **success publish only after the confirmed durable commit**, so a canonical-store failure can no longer leave raw odds committed with a fabricated success. A provider **observation captured immediately before `/odds`** orders the raw cache (`observedAt`) and stamps every generated snapshot's `capturedAt`, so an older/slower request can never overwrite newer raw or per-game state — a late stale request is a truthful **no-op / stale-observation** that publishes nothing. Filtered targets write ONLY their exact raw key (never the canonical per-game store). Public closing-line maintenance runs through the same durable-store transaction and skips the write when unchanged; a stale served fallback never downgrades the store.
- **Dormant automatic quota policy (C2-ready).** The reusable automatic gate (built, not called in production) validates `ODDS_API_KEY`, issues the **quota-free `/v4/sports`** usage probe with a single attempt (no retry — it is NOT an Odds data-provider call), and requires trustworthy `remaining ≥ estimated request cost + 50` (the canonical three-market/seven-bookmaker request costs **3**, so the floor is **53**). Missing/malformed/out-of-range usage headers **fail closed** (`quota-usage-untrustworthy`); a probe transport/HTTP failure is `quota-probe-failed`; trustworthy-but-below-reserve is `quota-reserve`. If the post-`/odds` response omits usage headers, an exact-empty result preserves the zero-cost balance while any uncertain billed outcome conservatively deducts the max cost of 3 (`odds-automation-estimate` source), corrected by the next zero-cost probe. Manual refresh is exempt from this hard reserve and keeps its existing low-quota warnings.
- **Dormant polling cadence (C2-ready).** A pure, deterministic target/cadence selector (built, wired to no scheduler): an eligible target needs a current-season canonical game with both participants resolved, a parseable future kickoff within the 7-day horizon, and a non-disrupted status; cadence is a 6-hour baseline with a 2-hour pre-kickoff window keyed on each **America/Chicago** slate date's FIRST kickoff (so a full Saturday slate is never accelerated all day), and `automaticNotBefore` overrides both.

## Guardrails while debugging

- **Do not spend provider quota from public paths** to "test" — use the admin-gated `refresh=1`. The public surfaces intentionally cannot cold-fetch.
- **Do not add name-matching or ownership logic outside `teamIdentity.ts` / `gameOwnership.ts`** to work around a miss — fix the alias/roster input instead (see [../architecture/identity-and-ownership.md](../architecture/identity-and-ownership.md)).
- **Do not recompute standings in a component** to reconcile a discrepancy — the canonical selector is the source of truth; a stale on-screen value is usually a missing tag invalidation, not a derivation bug (see [../architecture/standings.md](../architecture/standings.md)).
