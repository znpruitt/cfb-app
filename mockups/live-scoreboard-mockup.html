Mockup notes (not part of the design)
  • What this proposes: the scoreboard micro-component with three rendered state variants (live, final, scheduled), the promotion model — a game occupies exactly one section instead of rendering in both watchlist and live as it does today (overview.ts:1009 filters !== 'final', admitting in-progress by omission; Item 82 records it as a defect) — a two-column grid, and progressive disclosure per section.
  • Live state is neutral text plus a neutral dot, per the amber reservations in DESIGN.md :135, :215 and :281, none of which admit a live exception. (POLISH-007 governs the league-header confidence signal and owned-team-row copy, not game-card badges — it is not the authority here.) Two pieces of shipped amber are drift and must both go: the clock badges, and the amber card borders on live cards (OverviewPanel.tsx:734, border-amber-200/80 … dark:border-amber-900/70), which additionally collide with DESIGN.md :195 reserving card chrome for meaningful border signals.
  • Prefix slot is a classification marker, not just a rank. It holds an AP rank when the team is ranked, or an FCS marker when the opponent is FCS — mutually exclusive, since AP Top 25 is FBS-only. This preserves the FCS flag the Matchups panel surfaces today, which is real information: an FBS win over an FCS opponent means something different.
  • Neutral-site games need explicit handling. Away → home ordering assumes a home team; conference championships, bowls, CFP games and neutral openers have none. CFBD still assigns nominal away/home alongside a neutralSite flag, so ordering can stay unchanged and the condition becomes a metadata marker on the date line ("Neutral site"), as drawn. This must be in the component contract before Item 87 ships — otherwise postseason forces a widening of a shipped component.
  • Team records appear in every state, in one of two positions — decided. On scheduled rows the record is the anchor, since no score exists yet, and spread plus O/U sit on the odds footer. On live and final rows the anchor holds the score, so the record moves inline as a parenthetical after the team name — standard CFB scoreboard placement. Finals carry the post-game record including the result being read; a stale record on a final is bad data handling. The record therefore shifts position by state, which is accepted: the watchlist is legitimately a different layout, and the anchor consistently holds whatever number matters most in that state. The alternative — record inline everywhere with the scheduled anchor given back to the spread — was considered and rejected.
  • All records depend on Item 92. Until the CFBD records endpoint is wired, live and final rows omit the parenthetical and scheduled rows fall back to the spread anchor. The rows degrade cleanly in both cases.
  • The anchor holds a record; the record belongs to the line's primary identifier. A team-primary line (this scoreboard, in any state) anchors a team record. An owner-primary line (recap week records, standings, movement) anchors an owner record. Position stays constant across the app and context disambiguates — no label needed, and the team line stays at three elements plus an anchor, matching the live and final rows exactly. Spread and O/U move to the odds footer together.
  • Team records confirmed and ship as the scheduled-state anchor. CFBD GET /records?year= returns every team in one call (684 rows, all four divisions; 138 FBS matching teams.json exactly), supports in-season partials, and is keyed by numeric teamId — so the join needs no name resolution and sidesteps Item 83's collision. It also carries classification, giving a second independent source for the division label alongside PLATFORM-114. Budget is not a constraint: 341 used against a 5,000 limit; the ~1000/month figure is the live-scores reserve floor, not the ceiling. At weekly cadence this is roughly 4 calls/month. The spread fallback is not needed. Do not derive records from cached schedule + scores — a partial record is a false statement, not a missing one.
  • Recap alignment: the recap's notable-results scoreboards are the same component and inherit this rule. Their anchor is the score, since for a completed game the score is the relevant number — the anchor holds whatever number matters for that state (record when scheduled, score when live or final), which is also why the slot does not shift at kickoff. Open: whether recap notable results should additionally surface team records, which would require a fourth element on the line.
  • Row order is always away → home (CFB convention) in every state including Final. Ordering and emphasis are separable: position is fixed by home/away, weight marks the leader or winner. Several examples show the home side leading or winning from the bottom line.
  • The unknown state stays in Live and reads "Awaiting score." gameStateFromScore (gameUi.ts:51) returns a fourth value the three-section model must handle: past kickoff, no usable score. DESIGN.md :51-52 prescribes exactly this copy for the bounded post-kickoff gap and forbids both "Upcoming" and an unsupported "Live" claim. Routing it to Recent finals would assert the game finished — a stronger misstatement than either forbidden string — so it remains in Live with the status row reading "Awaiting score" and no Live badge, moving to Recent finals only when a final score attaches. The Live badge itself is unaffected elsewhere: those rows carry attached in-progress scores, and the prohibition is on claiming live without score evidence. Note: "Awaiting score" is placed in the status row rather than the per-team anchor, since it describes the game rather than either side; confirm that placement.
  • Section migration is immediate. A finalising game moves from Live to Recent finals as soon as it finalises, including while a section is expanded. This is a live surface and staleness is worse than motion. Client expansion state itself survives (useLiveRefresh.ts:443 is a state update on a mounted tree; router.refresh() preserves client state) — only the content changes beneath it.
  • Header rows are single-line by contract (nowrap + ellipsis on title, meta and status rows), because any wrap desynchronises team rows across a grid row. Consequence: the date/kickoff/broadcast line has a hard width budget and clips rather than wraps; precedence category names should stay to roughly two words.
  • Cards with no precedence reason reserve the title row and hide it, so team lines stay aligned across a grid row. Cost is a line of whitespace on untagged cards.
  • Three-column tier above 1300px container width. Rows use roughly a third of their column at two columns on a wide display, so the space is there. 1300 is 3×400px minimum column plus two 40px gaps: 400px is what the longest row needs — team, record, owner and score — and the Middle Tennessee State row in Live is the stress case. Below that the tier drops to two, then one under 760px.
  • Two costs worth weighing before adopting it. Row-major flow across three columns makes a kickoff-sorted section harder to follow — positions 1,2,3 / 4,5,6 read less naturally than 1,2 / 3,4, and the wider the grid the more the eye has to reset. And at current caps the saving is one row: six live games go from three rows to two. The gain is real only at full slate, which is also when ordering legibility matters most.
  • Two-column grid follows existing precedent rather than introducing it — FeaturedGamesList already ships grid-cols-1 sm:grid-cols-2 on this surface. Flow is row-major, matching RecapPrimitives.tsx:70 and FeaturedGamesList. Degradation uses a container query per DESIGN.md :120. The doc specifies the mechanism but no value, and three disagree in code (640 FeaturedGamesList, 821 recap, 760 here). 760 is chosen on content width — below it each card gets under ~350px, which clips team + owner + anchor on the longest rows — so the amendment should declare the game-grid value rather than inherit a sibling section.
  • Section titles are 17px/650 — a deliberate exception to DESIGN.md :224 (15px/500). At the documented size the section boundary sits one step above a team line at 14px and reads weakly against dense two-column content, worsened by three stacked sections. Documented as a game-section exception, not drift.
  • Broadcast network is free — buildCfbdGamesMediaUrl already runs via schedulePresentationRefresh.ts:273, cached year-wide, and joined onto rows by enrichScheduleItemsWithPresentation. No new call, no fallback needed.
  • Rank renders only for currently-ranked teams (rank is nullable); untagged sides simply omit the prefix.
  • Selection, ordering and caps defer to the watchlist precedence campaign. Do not fork prioritizeOverviewItems (overview.ts:428, called at :1019 and :1025 off deriveOverviewHighlightSignals in gameTags.ts:310).
  • On colour — the surface is neutral because two decisions are deferred, not because colour is forbidden. Precedence eyebrows are slated for hues in INSIGHTS-017-PALETTE and render neutral here as placeholders. The preview cycles four candidates with green live held constant; these are scoping input for 017, not assignments.
  • Proposed colour: bronze eyebrow (#c9a66b) with green live. Mockup defaults to this; the toggle cycles alternatives. Ranked bronze > sky > neutral > fuchsia. Adjacency is not disqualifying — a reservation binds a token to a purpose, not a hue neighbourhood, and bronze (desaturated tan) is not champion amber (#BA7517, dark saturated gold). Temporal separation settles it: the live league page renders podium cards for #1–#3 in neutral chrome with no champion treatment, so amber is dormant through the season and bronze competes with nothing until a title is actually awarded. Fuchsia is rejected: complementary clash against green, and it sits between TRAJECTORY and HISTORICAL. Final hues are assigned by INSIGHTS-017-PALETTE; this is a ranked recommendation into that work, not a local assignment.
  • Palette allocation is the real question for 017, not leftovers. Reservations can be re-cut when a colour does more work elsewhere. Ranked by how much colour actually contributes: live status is time-critical and glanceable, and colour is the whole signal — highest value. Champion is rare but emotionally weighted and gold is irreplaceable — keep. Deltas already carry an arrow and a number, so colour is reinforcement rather than the sole carrier — it could survive a narrower claim. Interactive blue is conventional but links also carry position and underline. Insight category microlabels are the weakest use: five-plus hues spent on 10px labels whose words already state their meaning — and they are the tokens already colliding (8 categories over 5 hexes, with CAREER's #5DCAA5 unreachable). If 017 needs headroom, that is where to reclaim it, rather than squeezing new signals into gaps between existing tokens.
  • Live status is green, under a context-scoping rule that already governs the app. Green ships in at least six distinct meanings — the sharpest proof being deltaTextColor (OverviewPanel:95-99, positive delta) and gbDeltaColor (:298-302, negative delta, because gaining ground is good), the same token on opposite numeric signs, disambiguated purely by host element. The rule 017 should document, with the enforcement clause: a hue carries exactly one meaning within a component family; context scopes meaning across families, never within one. That makes the delta pair legal and forbids the case below.
  • Featured is a separate axis from state. State moves games between sections; Featured exempts a game from that movement — it enters when selected and stays through scheduled, live and final. Featured games therefore appear only in the Featured tile, not in the state sections, preserving the promotion model's one-game-one-place rule. The tile carries the reason with substance ("Whited leads Chamness 44–25") rather than a bare label, since a game earns promotion out of the slate only if the reason is worth stating. Deliberately small — at five games it is another list with a nicer name.
  • Featured resolves the green-final question. Converting Featured to the scoreboard component retires the third stateBadgeClasses call site (:931) alongside :746 and :843, so Overview carries no green-final and green-live ships in this campaign with no dependency on Item 90.
  • Featured is the insights system with a game hook, not watchlist curation. The watchlist asks which games are worth watching on football criteria; Featured asks which games activate something the league already knows. The rivalry insight already ships in the feed — Featured is that same fact bound to a game about to be played between those owners. Selection therefore belongs with the insights pipeline, not prioritizeOverviewItems: the criteria are the existing insight taxonomy rather than a new one, the over-firing risk is likely already handled by the registry's priority and suppression machinery, reason labels inherit whatever hue INSIGHTS-017-PALETTE assigns to their category, and copy generates from the insight as feed items already do. Only pair-anchored insights qualify — "longest active title drought" has no game to attach to. New rule required: an insight surfaced in Featured should be suppressed from the feed that week, or the page states the same fact twice.
  • Open on Featured: maximum count; whether zero qualifying games hides the tile; whether featuring resets weekly or a game can carry across weeks; and copy tone — "toilet bowl" reads as league banter rather than an insult only because this league's voice supports it, so auto-generated copy about members finishing last is an owner call, not a default. Selection logic belongs with the watchlist precedence work, not here.
  • Eyebrow and title-row strings are placeholders, including "Top matchup." Item 87 records that label as false: gameTags.ts:441 fires it from isTopOwnerGame — true when either owner is top-three — while the identically-worded eyebrow elsewhere means "best game on the slate," and the two contradicted in production. Implementation must consume the renamed labels, not these strings. Hues are assigned in INSIGHTS-017-PALETTE; semantics are fixed by the Item 87 rename.
  • Scoreboard row contract is a superset of what INSIGHTS-026b's enrichment stage needs (final-only rows for notable results). This file defines the full contract — three state variants, rank prefix, anchor slot, odds footer, reserved title row — so 026b's enrichment prompt consumes it rather than shipping a narrow version this campaign then has to widen.
